# Discord Manager 2.0 Base

방송인용 Discord 서버를 구성하는 봇의 1차 범용화 기반입니다. 실행 진입점은 `main.py`입니다.
하나의 봇으로 여러 서버를 관리하며, 생성한 역할·분류·채널·닉네임 안내 ID와 설치 상태를 `guild_id`별로 저장합니다.
현재는 기본 프리셋 하나만 제공합니다.

## 기본 구조와 기존 기능

| 분류 | 채널 |
| --- | --- |
| 안내 | 규칙, 공지, 방송공지 |
| 커뮤니티 | 자유채팅, 사진 및 영상, 닉네임 제출, 시참 대기실, 시참, 시참 예비용 |
| 합방 | 합방 채팅, 합방, 합방 예비용 |
| 운영 | 운영관리 → 닉네임_DB → 관리기록 |

분류 4개, 텍스트 채널 10개, 음성 채널 5개입니다. 사진 및 영상은 자유채팅 바로 아래에 배치합니다.

- `Owner` / `Manager`: Administrator. Owner 역할은 서버 소유자에게 부여합니다.
- `Streamer`: 합방 채널 접근 가능. `Viewer`: 일반 시청자. 신규 일반 멤버에게 자동 부여합니다.
- 기존 기본 채널 권한을 유지합니다. 닉네임 제출은 안내 열람 가능, 직접 메시지·스레드 작성 불가입니다.
- 시참 음성방은 기존처럼 일반 멤버에게 숨기고 관리자가 대기실에서 이동시키는 방식입니다.
- `/방송공지`: 방송공지 채널에 공지 전송. 전체/역할 멘션 차단, 사용자 멘션 허용.
- `/닉네임`과 persistent 버튼: 같은 모달로 비공개 제출. `닉네임_DB`에 서버 닉네임/게임 닉네임/게임명을,
  `관리기록`에 사용자명/ID와 UTC+9 제출 시각까지 상세 기록합니다. DB가 없으면 관리기록으로 폴백합니다.
- 안내 생성·갱신·pin, 입퇴장·역할 변경 기록, Viewer 자동 부여를 유지합니다.
- 런타임 명령과 이벤트도 기록된 ID를 사용합니다. 같은 이름의 사용자 리소스에 대신 기록하거나 권한을 부여하지 않습니다.

## setup 명령

`/setup`은 그룹일 뿐 자체 실행 동작은 없습니다. 서버 소유자 또는 **등록된 Manager 역할**의 멤버가 실행합니다.
미설치 서버의 최초 설치는 서버 소유자가 실행합니다. 기존에 사용자가 만든 동명 Manager 역할은 권한 근거로 쓰지 않습니다.

| 명령 | 동작 |
| --- | --- |
| `/setup start` | 설치/복구 내용을 먼저 표시합니다. 실행자 본인이 2분 안에 **설치 적용**을 눌러야 생성·수정합니다. 정상 설치된 서버에서는 추가 생성 없이 종료합니다. |
| `/setup check` | 설치 상태, 역할·분류·채널, 권한, topic, 채널 순서, 시스템 메시지 채널, 닉네임 안내/버튼/pin을 진단합니다. Discord 서버와 저장 파일을 수정하지 않습니다. |
| `/setup sync` | 등록된 DM 리소스를 ID로 찾아 누락 항목을 생성하고 이름·권한·배치·안내를 복구합니다. 최초 설치는 start로 안내합니다. 부분 설치는 sync로 재시도할 수 있습니다. |
| `/setup reset` | 삭제할 리소스의 이름과 ID, 보존할 항목을 모두 표시합니다. 실행자 본인의 확인 뒤 해당 DM 리소스만 삭제합니다. 자동 재설치는 하지 않습니다. |

확인 시 실행자의 권한을 다시 검사합니다. 확인은 한 번만 사용할 수 있고 봇 재시작/시간 만료 후에는 명령을 다시 실행해야 합니다.
reset은 확인 이후 상태가 달라지면 실행하지 않고 목록을 다시 확인하도록 요청합니다.
같은 guild의 setup 작업은 동시에 실행하지 않습니다. 서로 다른 guild는 별도 잠금과 상태를 사용합니다.

### reset의 변경된 범위

기존의 전체 서버 삭제 후 재구축 로직은 제거했습니다. **DB에 DM 생성 이력이 남은 리소스만 삭제 후보**가 됩니다.
이름만 같은 사용자 역할·채널은 삭제하지 않습니다. 상태가 없거나 출처를 확인할 수 없는 리소스도 자동 인수·삭제하지 않습니다.

확인한 DM 채널의 메시지 기록(닉네임_DB와 관리기록 포함), 삭제하는 DM 역할의 멤버 배정도 삭제됩니다.
실제 삭제 목록과 이 영향을 확인 화면에 명시합니다. 다시 설치하려면 `/setup start`를 실행합니다.

사용자 채널이 들어 있는 DM 분류, 사용자 채널 권한에 사용 중인 DM 역할, 봇 역할보다 위에 있는 역할은 보존합니다.
삭제에 실패한 리소스의 ID는 저장소에 남겨 재시도합니다. 삭제 직전에도 하위 채널/역할 사용 여부를 다시 확인합니다.
다만 Discord API는 일괄 트랜잭션이 아니므로 중간 실패 시 일부만 정리될 수 있습니다.

## 소유권과 기존 서버

- 생성 전에 현재 Discord 역할/채널을 REST로 조회합니다. 저장 ID를 이름보다 우선합니다.
- 관리 중인 리소스가 이름만 바뀌어도 ID로 재사용합니다. sync는 표시 이름을 정의값으로 되돌립니다.
- 저장 ID가 없거나 삭제됐는데 같은 이름의 사용자 리소스가 있으면 **수정 전에 충돌을 보고하고 중단**합니다.
  이름은 공백/하이픈을 동일하게 취급합니다. 임의로 인수하거나 같은 이름으로 복제하지 않습니다.
- DM 채널의 멤버 개인 예외와 추가 역할 overwrite는 보존합니다. 사용자 채널·역할을 직접 수정/삭제하지 않습니다.
  사용자 채널이 DM 분류 권한을 동기화해서 사용하는 경우에는 해당 분류의 권한 변경이 영향을 줄 수 있습니다.
- 서버 `@everyone` 역할 자체의 권한은 변경하지 않습니다. 기존 전체 멘션 차단은 DM 채널의 overwrite로 적용합니다.
- 시스템 메시지는 기존 기능대로 DM 관리기록에 연결합니다. start 확인 화면에 이를 표시합니다.

**이전 버전으로 이미 만든 서버의 자동 마이그레이션/인수는 제공하지 않습니다.** 이전 버전에는 생성 ID 저장 이력이 없습니다.
그런 서버 또는 상태 파일을 잃은 서버에서는 동명 충돌로 중단합니다. DB 백업을 복원하거나,
운영자가 기존 리소스를 검토하고 충돌을 해소한 뒤 설치해야 합니다. 봇이 이름만으로 소유권을 추측하지 않습니다.

## 코드 구조와 커스터마이즈

| 파일 | 역할 |
| --- | --- |
| `config.py` | 기본 표시 이름, 닉네임 안내/모달 문구 |
| `preset.py` | 현재 base의 역할·분류·채널 구조, 안정적인 논리 키, 권한 정의. Discord API 호출 없음 |
| `resources.py` | 조회·소유권 충돌 검사·생성/복구·진단·reset 계획/실행 |
| `state.py` | `StateStore` 인터페이스, `GuildState`/`ResourceRecord`, SQLite 구현 |
| `main.py` | 봇 실행, 슬래시 명령/확인 View, 닉네임 모달/안내, 이벤트 |

표시 이름과 문구는 `config.py`에서 변경합니다. `ROLE_NAMES`·`CATEGORY_NAMES`·`CHANNEL_NAMES`의 **키는 유지하고 값만 변경**하세요.
`role:viewer`, `category:community`, `channel:nickname` 같은 논리 키에 ID가 연결되므로 이름 변경 후에도 기존 ID를 재사용할 수 있습니다.
지금의 config는 모든 guild에 공통인 기본 정의입니다. 서버별 사용자 지정 옵션 UI나 추가 프리셋은 아직 없습니다.

`StateStore.load/save`를 통해 저장 방식을 교체할 수 있습니다. 외부 DB나 웹 서비스는 필요하지 않습니다.

## 실행 및 상태 저장

Python 3.11 또는 3.12:

```bash
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
python main.py
```

```env
DISCORD_TOKEN=your_token_here
DM_STATE_PATH=data/dm.sqlite3
```

봇에 Administrator 권한을 주고 봇 역할을 DM이 관리할 역할보다 위에 둡니다.
Discord Developer Portal에서 `SERVER MEMBERS INTENT`를 켜야 Viewer 자동 부여와 멤버 이벤트가 동작합니다.

SQLite는 guild별 설치 완료 여부, 생성 리소스의 종류/ID/생성 여부, 안내 메시지와 부모 채널 ID, 상태 revision을 저장합니다.
닉네임 제출 내용 자체는 기존처럼 Discord 비공개 기록 채널에만 저장하며 SQLite에는 저장하지 않습니다.
각 생성/삭제 성공 직후 ID를 저장하고 마지막까지 성공해야 설치 완료로 표시합니다.
읽기 요청은 파일을 만들거나 갱신하지 않습니다. 손상·지원하지 않는 버전·쓰기 실패는 오류로 처리하며 빈 상태로 간주하지 않습니다.

**배포 시 `DM_STATE_PATH`의 디렉터리를 영속 볼륨에 두고 백업하세요.** 임시 파일시스템에서는 재배포 후 소유 기록을 잃습니다.
현재 지원 범위는 **하나의 봇 프로세스/하나의 DB**입니다. 여러 프로세스/복제본의 분산 잠금은 구현하지 않았습니다.
Discord 응답 성공과 SQLite 저장 사이의 프로세스 종료/디스크 실패는 원자적으로 처리할 수 없습니다.
이때 기록되지 않은 리소스는 다음 실행에서 동명 충돌로 보존하고 수동 확인을 요청합니다.

## 검증과 남은 작업

```bash
python -m compileall -q main.py config.py preset.py resources.py state.py tests
python -m unittest discover -s tests -v
```

실제 discord.py 객체를 사용하는 모의 REST 백엔드로 설치 확인, 재실행, check의 읽기 전용 동작, 채널/안내 복구,
사용자 리소스/overwrite 보존, reset 확인/부분 실패/재시도, 두 guild 분리, 재시작/캐시 지연, 기존 기능을 검증합니다.
실제 Discord 서버에서 설치·reset은 실행하지 않았습니다. 테스트 서버에서 API 동작과 권한을 확인한 뒤 운영에 적용하세요.

후속 작업: 기존 서버의 명시적 인수/마이그레이션, 서버별 옵션과 설치 UI, 다중 프로세스 조정.
웹 대시보드·OAuth·계정·과금·외부 DB·추가 프리셋은 이번 범위에 포함하지 않습니다.
